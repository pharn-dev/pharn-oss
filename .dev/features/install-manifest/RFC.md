# RFC — pharn-oss declares its install manifest (`pharn-install.json`)

- Status: **Accepted (owner delegated, 2026-11-16)**
- Renumbered 2026-11-17: #453 released 7.20.0 first, so the first release carrying the manifest is 7.21.0.
- Linear: CORE-193 (C8.1), epic CORE-157 (C8: install what pharn-oss declares). Consumer: CORE-194 (C8.2, pharn-cli).
- Related decision: CORE-186 (C6.1 support policy: the `flat` layout is deprecated in pharn-cli v0.20.0 and removed in
  v0.22.0; `PHARN_ROOT_FALLBACK_DOCS` retires with it).
- Schema: [`docs/install-manifest.md`](../../../docs/install-manifest.md). Spike: [`SPIKE-DIFF.md`](SPIKE-DIFF.md).
  Plan: [`PLAN.md`](PLAN.md).

## Problem

pharn-cli builds an install from this repository's internals instead of from a declaration:

- the capability frontmatter rules, ported in `capability-index.ts` and held to a vendored `validate.mjs` by a
  differential test;
- the `models` rules, ported in `model-config.ts` and held to a vendored `check-model-config.mjs` by a parity test;
- the tree layout — which files are tests, which directories are fixtures, which surfaces exist, two layouts, the
  root-doc fallbacks — in `install-manifest.ts`, `install-surfaces.ts` and `layout.ts`.

Every upstream change needs a lockstep CLI release: pharn-cli 0.18.1 was 833 lines for one new stage name, 1 of them in
`src/`. And a closed surface list in the CLI cannot see a surface added here: this repository shipped
`.claude/agents/pharn-review-lens.md` from 6.64.0, and the CLI did not install it until its own C2.7 release.

## Decision

This repository commits a generated `pharn-install.json` at its root, and the CLI installs what it declares (CORE-194).
The owner's decisions, recorded as decided:

1. **Name and place.** `pharn-install.json` at the repository root, committed, generated by
   `.dev/floor/gen-install-manifest.mjs` from this repository's own walkers and checkers, and drift-checked on every
   pull request by `.dev/floor/check-install-manifest.mjs` (the capability-catalog pattern). Both join the existing
   `docs:generate` / `docs:check` scripts, so CI's "Docs drift check" step runs the check with no workflow change. It
   ships inside the codeload tarball only — no release asset. A release workflow cannot add a file to the tagged
   commit's tarball, and `--ref main` needs the manifest on every commit, so the file is committed.
2. **Contents.** `schemaVersion: 1`; `skillsVersion` (from `SKILLS_VERSION`, held equal by the drift check); **no
   `minCli`** (`MIN_CLI` stays the one source the CLI already reads); `files` with every installable file's source
   `path`, `dest`, `surface`, owning `capability` (when any), `policy` and `sha256` over raw bytes;
   `capabilities: [{name, role, applies, dir}]`; the `models` defaults and rules, taken from the existing checker's own
   exports; the `layout` and the install-root globs.
3. **Exclusions in one place.** Test files, floor test fixtures and every other non-installable file are left out by
   one declaration, `.dev/floor/install-manifest-core.mjs` (`INSTALL_SURFACES`, `CAPABILITY_SUBTREES`,
   `GLOBAL_EXCLUDE`, `LEGACY_INSTALL_ROOTS`).
4. **Versioning.** Decided by CLAUDE.md "SKILLS_VERSION discipline" and `check:surface-bump`: see "Versioning" below.
5. **This RFC** lives with the feature's records, the repository's design-record convention (there is no separate RFC
   directory); the schema is documented in `docs/`.
6. **Spike.** The prototype's output was diffed against the CLI's `installManifest` for the current release in both
   layouts, and every difference is explained in [`SPIKE-DIFF.md`](SPIKE-DIFF.md).

Decisions taken at this increment's plan gate (GATE 1):

- **One `dest` per file, at the `pharn` layout.** A manifest exists only in trees generated from 7.21.0 on, and every
  one of them is the `pharn` layout; the CLI installs a clone in the clone's own layout (`detectLayout`). The flat
  layout ended at `b42684b5` (#86, 2026-07-10, `SKILLS_VERSION` 1.0.0), before the first release tag (v7.1.2). A flat
  `dest` would describe an install no CLI can perform from a manifest-bearing tree. The flat layout survives only as
  `installRoots.legacy`, so the CLI can still bound an older flat install's record keys until it retires flat (v0.22.0).
- **A pre-manifest tree has no manifest.** Any ref older than 7.21.0 — every flat ref included — carries no
  `pharn-install.json`, and the CLI falls back to its current derivation for it, for one minor (CORE-194, per the
  CORE-186 support policy).
- **The models rules come from the checker's bindings.** `pharn/floor/check-model-config.mjs` exports
  `PRODUCT_STAGES`, `MODEL_ALIASES`, `MODEL_ID_RE` and `EFFORT_ENUM`, and running it is now gated on `import.meta.main`
  inside `main()`, so importing it runs nothing. Its CLI behaviour, messages and exit codes are unchanged, and the
  lines other tests pin stay byte-identical. The fallback key `"default"` is a literal in the checker; the manifest
  carries it as `fallbackStage`, bound by a test that runs the checker on a block without it.
- **`applies` takes the CLI's shape**: the string `"universal"`, or an array of archetypes (`ssr`, `backend`, `spa`,
  `lib`), so the CLI validates it against its own enums with no translation.

## Versioning

- `pharn-install.json` itself is **outside** the bump-triggering product surface. The rule applied: CLAUDE.md
  "SKILLS_VERSION discipline" names the set concretely (the capability tree, `pharn/floor/*.mjs` and `*.json`, the four
  trusted docs, and the product `.claude` surface), and `check-surface-bump.mjs`'s `PRODUCT_SURFACE` is bound to that
  list. A root installer-metadata file is not in it: like `SKILLS_VERSION` and `MIN_CLI`, the manifest is read by the
  installer and never copied into an install. Regenerating it never needs a bump of its own.
- This increment bumps anyway, **7.20.0 → 7.21.0 (minor)**, because it changes `pharn/floor/check-model-config.mjs`,
  which is in the set ("any change that alters product-surface bytes MUST bump"); minor, because a floor CLI gains an
  exported interface and the tree gains an installer-facing declaration. When the owner merges it, `release.yml` tags
  v7.21.0, the first release carrying the manifest. Until then the CLI develops against this branch's manifest.
- `MIN_CLI` is unchanged: an older CLI ignores the file.
- A later change to any installed file, and every `SKILLS_VERSION` bump, changes the manifest; `docs:check` fails until
  it is regenerated.

## Schema (summary)

The full field reference, the policy and surface enums, the glob grammar and the list of what a consumer must validate
are in [`docs/install-manifest.md`](../../../docs/install-manifest.md). In short:

```text
schemaVersion  1
skillsVersion  "X.Y.Z"
layout         {name: "pharn", marker, capabilitySubtrees: {griller, lens}}
capabilities[] {name, role: griller|lens, applies: "universal" | [ssr|backend|spa|lib…], dir}
files[]        {path, dest, surface, capability?, policy: managed|if-absent, sha256}
models         {defaults: <root pharn.config.json models block>, rules: {fallbackStage, stages, aliases, modelIdPattern, effortLevels}}
installRoots   {include[], exclude[], legacy[]}
```

## Trust

- **Provenance** is the tarball's: the same release-tag resolution the CLI already uses (`--ref latest`, or an
  explicit `--ref`). The manifest adds no fetch path and so no new trust question.
- **The manifest is data, never executed.** The CLI validates it as untrusted input: schema, path containment, its own
  allowlists for names and enums, and the `sha256` of every file after extraction, refusing the install on any mismatch
  before writing (CORE-194). The generator's own refusals are listed in the schema doc; they help an honest tree and
  bind an attacker to nothing.
- No change to `pharn/THREAT-MODEL.md` or `pharn/LIMITS.md` is needed here: the manifest adds no capability to an
  installed project. The CLI's THREAT-MODEL describes the manifest's trust under CORE-194.

## Alternatives rejected

- **A release asset.** A second download with its own trust question, and absent for `--ref main`.
- **A `dest` per layout.** Describes installs no CLI can perform from a manifest-bearing tree (see above).
- **`minCli` in the manifest.** A second copy of `MIN_CLI` (lessons-learned L35).
- **Reading the models rules from the checker's source text**, as `route-token-core.test.mjs` does. A parser over
  source pins a spelling, not the binding; the export is the binding itself.
- **A separate `model-config-rules.mjs` module.** It would move the `MODEL_ALIASES` literal out of the checker and
  force an edit to an existing source-parity test, for no gain over a side-effect-free import.

## Bounds (P0)

- The drift check guarantees **byte equality** between the committed manifest and the rules applied to the tree —
  consistency, never correctness (L43). A wrong rule regenerates green. Two tests bind the rules to referents: every
  `PRODUCT_SURFACE` path is declared, and the installable paths outside it are exactly `LICENSE`,
  `pharn/features/README.md` and `pharn/floor/README.md`.
- That the tarball carries the declared bytes holds while `.gitattributes` normalizes to LF and declares no
  `export-ignore`. Nothing checks either; the CLI's sha256 verification is the check.
- `installRoots.legacy` is declared history, not derived.
- Observation, not fixed here: `pharn/floor/README.md` is installed but outside `PRODUCT_SURFACE`, so an edit to it
  reaches installs without a `SKILLS_VERSION` bump.

## Migration (CORE-194)

1. With a manifest in the clone: validate it, verify every file's sha256 after extraction, and install from it — the
   fixed-surface files plus the selected capabilities' files, `.claude/settings.json` only when absent, `LICENSE` at
   its declared `dest`. Use `capabilities` for the index and `models` for the defaults and rules.
2. Without one: the current derivation, for one minor.
3. After that minor: delete the frontmatter port, the `model-config.ts` copy, the vendored pharn-oss files and their
   differential and parity tests, `FLOOR_TEST_FIXTURES_DIRS` and, with `flat` (v0.22.0), `PHARN_ROOT_FALLBACK_DOCS`.
