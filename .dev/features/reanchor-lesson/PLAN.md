## Why (P7 — the trigger)

The trigger is a recorded failure, not a hypothesis. In the CORE-314 run, `origin/main` moved four times. After the
first two merges the run re-ran build Step 0 (setter, then `--anchor`), as the batch brief directed. The build's two
files had been written before the last anchor, so verify's reconcile read `CLEAN` with `reconciled: 0`, and the
record's P0 section first claimed a reconcile the window did not hold
(`.dev/features/delegated-signoff-2026-11-23/VERIFY.md`, "Orchestration notes"; `REVIEW.md`, first advisory
finding). After the last two merges the run did not re-anchor, and reconcile listed all 24 upstream paths under
`merged` with no escape. That run's Step 2b could not ask its question (a subagent has no interactive gate), so it
recorded `lesson: error …` and left the candidate in `REVIEW.md` § "Proposed lesson candidate". On 2026-11-23 the
maintainer asked, in chat, to promote that lesson through `/pharn-dev-ship`.

No repository file tells a contributor to re-anchor after merging `origin/main` (searched live:
`grep -rn -i "re-anchor"` over `.claude/commands/`, `.dev/guides/`, `CONTRIBUTING.md` and the reconciliation
contract finds only `/pharn-loop`'s retry rule and the contract's "never re-anchor to silence a RED"). The advice
lived in a batch brief outside the repository. So the increment changes no command or guide: the lesson is the
deliverable, and it reaches canon only through the promote command's own gate.
