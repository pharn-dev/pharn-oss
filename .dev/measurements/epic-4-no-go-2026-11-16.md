# Four epic-4 candidates: close (2026-11-16)

A decision record for Linear CORE-96 (`plan-decisions-budget`), CORE-97 (`auto-size-quick`), CORE-98
(`stage-read-trim`) and CORE-99 (`spec-self-review`): the four candidates of epic 4 that the 2026-11-11 baseline rated
**no-go**. The answer for each is **close**. Nothing is built.

- **Written by:** the `epic4-no-go-2026-11-16` increment (plan, grill and ship records in
  `.dev/features/epic4-no-go-2026-11-16/`).
- **Dated** by its name. Every figure marked `S` was read on **2026-11-16**, with this repository at `155d1205`
  (7.19.0, the tip of `origin/main` after a fetch).
- **The baseline** is `.dev/measurements/loop-baseline-2026-11-11.md`, taken at 7.10.3 over 36 `/pharn-loop` runs on
  7.1.4 and 7.3.0. Its ledger figures are cited here, not re-derived (section 1).
- **Changes:** this file and one CHANGELOG entry. No product-surface byte, no `SKILLS_VERSION` bump.

## Labels (the baseline's convention, its §2 "Labels")

- **Source:** `O` — an earlier record, cited by path (here mostly the baseline, `[O·m]` = a figure it measured); `S` —
  static, read in this repository on 2026-11-16.
- **Precision:** `m` — measured; `e` — an estimate from measured numbers, with its formula.
- Bytes are UTF-8 bytes of the file as git holds it at the named ref, `\r\n` folded to `\n` (the command budget's

## The decision

**Close all four.** The orchestrating model made this decision under the user's delegation for this batch ("You make
all decisions"). The maintainer did not sign it off in person, and may overturn it. Each section below gives the
ticket's own close condition, the baseline figure behind the no-go, what main can have moved since 7.10.3 and what it
reads now, and the reopen trigger. The two reopen thresholds that are numbers (CORE-96's 30 runs, CORE-98's 10%) were
chosen at this increment's GATE 1, by the same delegated decision; neither is measured.

## 2. CORE-96 `plan-decisions-budget` — close

- **The ticket:** ask plans for decisions rather than code, and print the plan's size as a NOTE. Its close condition,
  quoted as DATA: "Earlier records suggest plan-stage time follows request count more than plan bytes. If the baseline
  confirms that, this task loses most of its case and should be closed."
- **The baseline confirms it.** Over the 33 runs with both figures, plan minutes correlate 0.76 with plan-stage
  requests and 0.43 with `PLAN.md` bytes [O·e, Pearson's r, baseline §9]. Plans have a median of 28,955 B (5,963–55,844,
  n = 34) [O·m]. A correlation is an association, not a cause: it says plan bytes are the weaker of the two predictors
  in these runs, not that shrinking a plan would leave its time unchanged.
- **On main:** `pharn-plan.md` is 26,749 B, unchanged since 7.10.3 (`git log v7.10.3..HEAD` over the file prints nothing) [S·m], against a 29,696-byte ceiling: 2,947 B of headroom. The ticket's
  "25,556 B against a 26,624 ceiling" was the 7.3.0 file and the pre-7.8.0 ceiling. No plan-stage change since 7.10.3
  bears on the correlation.
- **What no ledger covers:** re-plan rounds (7.8.0), in which `/pharn-plan` reads the previous round's plan, findings
  and triage. There, plan bytes are an input to the next request, so the association could differ. No run on 7.8.0 or
  later has a ledger (baseline §10).
- **Reopen when** either: (a) over 30 or more full runs, plan-stage minutes (or plan-stage weighted cost) correlate with
  `PLAN.md` bytes at least as strongly as with plan-stage requests; or (b) a ledger that covers re-plan rounds shows a
  re-plan round's cost rising with the bytes of the plan it reads. 30 is a chosen sample size, close to the baseline's
  33, not a derived one.

## 3. CORE-97 `auto-size-quick` — close

- **The ticket:** print a "fits quick" line when a full SPEC has the quick shape. Its close condition, quoted as DATA:
  "Start only if the baseline shows a material share of full runs with three or fewer criteria. Otherwise close it."
- **The baseline:** 4 of 36 full runs had three or fewer criteria (`ln1-dogfood`, `ln2-launch-alerts`,
  `bl3-drop-user-billing`, `lg3-remove-files`, 3 each) [O·m, baseline §9]: 11.1% [O·e, 4 / 36]. All four stopped where
  quick mode runs the same step: `ln1` at S10 in the plan stage (`unlisted-ask`, a CI workflow the plan setter refuses),
  `ln2` red at entry (`typecheck` out of heap), `bl3` and `lg3` unmeasured at entry (`test` timed out) [O·m, §7].
- **What main changed:** the closure now rests on the share alone. The second reason is weaker than it was at 7.10.3.
  7.16.0 lets a project declare `gates.timeoutMs`, a longer per-gate timeout at entry, regress and verify (CORE-87).
  With one declared, the two `test`-timeout stops (`bl3`, `lg3`) might not recur, and those runs would go on to the
  steps quick mode leaves out: the full grill with triage, and regress's base side. Whether they would is not measured:
  no run on 7.16.0 exists, and the project has declared no timeout. 7.14.0's S14c (a cached red stops a repeat run on the
  same tree) stops earlier in both modes alike.
- **What did not change:** quick mode's meaning. The 7.11.0–7.19.0 CHANGELOG sections mention quick only in two
  byte-count notes of 7.18.1 [S·m, `grep -n -i quick` over those sections]. `pharn-ship-quick.md` is unchanged since
  7.10.3, and `pharn-loop-quick.md` gained only `[--refresh-entry]` on its entry line (7.14.0) [S·m, `git log` and
  `git diff v7.10.3 HEAD` on both]. The mode is still bound at entry: the Stop-guard marker records it before any SPEC
  exists, and `check-loop-decision.mjs` refuses a record whose mode differs (`MODE_UNWITNESSED`). `pharn/LIMITS.md §3a`
  still states that nothing measures whether a change is small and that there is no automatic proportionality. A
  "fits quick" line would not change that: it would print a count, and a person would still choose the mode.
- **Reopen when** both: (a) a ledger set of full runs on 7.16.0 or later has a larger share of runs with three or fewer
  criteria than the baseline's 4 of 36; and (b) at least one of those runs reaches a step quick mode leaves out (the full
  grill with triage, or regress's base side). The threshold in (a) is the baseline's own share, chosen at GATE 1, not a
  derived "material" level.

## 4. CORE-98 `stage-read-trim` — close

- **The ticket:** stages read `pharn/ARCHITECTURE.md §6` through an extract instead of the whole file. Its close
  condition, quoted as DATA: "Start only if the baseline rates it go; otherwise close it." The baseline rated it
  **no-go** [O, §12], so the condition to close is met as written. The rest of this section checks whether main has
  moved the figure behind the rating.
- **The baseline:** outside §6 the file was 19,392 B on 7.10.3 [O·m], about 4.8k tokens [O·e], against a routed stage
  agent whose first request was 94–97k tokens and whose last was 190–300k [O·m, baseline §3].
- **On main:** outside §6 is 19,582 B [S·m], about 4.9k tokens [S·e, 19,582 / 4 = 4,895.5, taken as 4,896 below]; §6 itself is unchanged at 6,347 B.
  Two commits touched the file since 7.10.3, `259f27dd` (7.18.0) and `08e33698` (7.19.0) (`git log v7.10.3..HEAD` over the file) [S·m]. Four stage commands tell the agent to read the
  §6 contract or row ("Read the `pharn/ARCHITECTURE.md §6` …") (`pharn-spec.md:41`, `pharn-plan.md:52`, `pharn-grill.md:51`, `pharn-build.md:51`); test,
  regress and verify list the file in `reads:` and cite it without a read instruction [S·m, `grep -n ARCHITECTURE`].
  Whether an agent reads the whole file or only §6 is not recorded anywhere.
- **The denominator moved.** 7.19.0 (CORE-107) requests routed stage agents as the lean `pharn-stage` type. Its probe
  measured a first request of 20,973 tokens for `pharn-stage` against 47,017 for `general-purpose`, a gap of 26,044, on
  one model, with a one-line prompt, in this repository's probe tree (`.dev/features/lean-stage-agent/MEASUREMENTS.md`
  §2) [O·m]. What 4.9k tokens is as a share, under each denominator available, all `[S·e]` and advisory:

| denominator                                                                      | tokens        | 4,896 as a share |
| -------------------------------------------------------------------------------- | ------------- | ---------------: |
| the probe's bare `pharn-stage` first request (no brief, no command body)         | 20,973        |            23.3% |
| the baseline's routed first request less the probe's gap (94k and 97k, − 26,044) | 67,956–70,956 |        7.2%–6.9% |
| the baseline's routed first request, `general-purpose` (today's installed case)  | 94,000–97,000 |        5.2%–5.0% |
| the baseline's routed last request                                               | 190k–300k     |        2.6%–1.6% |

- **How to read the table.** The first row is an upper bound, not a real stage: a routed stage's first request also
  carries its brief and, after a Read, its command (`pharn-plan.md` alone is 26,749 B). The second row assumes the
  probe's gap carries over to a project's routed stage; the probe ran in another tree with other instruction files, so
  that is not measured. And in an installed project every routed stage still runs as `general-purpose` until pharn-cli
  copies `.claude/agents/` (`cli-install-agents`), so the third row is today's case there. On every row but the bare
  probe the share stays under the 10% the trigger below names.
- **Reopen when** both: (a) a measured first request of a routed stage on the `pharn-stage` type, in an installed
  project, is small enough that `ARCHITECTURE.md` outside §6 (bytes / 4) is at least 10% of it; and (b) a transcript
  shows a stage agent reading the whole file rather than §6. 10% is a chosen threshold, not a derived one. CORE-90's
  probe set would then say whether an extract keeps quality.

## 5. CORE-99 `spec-self-review` — close

- **The ticket:** an advisory pass over a model-approved SPEC's criteria for consistency, before it is pinned. Its
  close condition, quoted as DATA: "P7: the evidence is one read case out of 36 runs, the same bar the 7.4.0 change
  used. Start only if the baseline finds more."
- **The baseline finds no more.** One stop is a contradiction between criteria: `fl1-test-results`, S10
  (`unlisted-ask`) in the plan stage [O·m, §7]. Two more are criterion defects of other kinds that a consistency pass
  does not target: a wrong fact in a criterion (`github-app-foundation`) and a criterion the shell cannot observe
  (`gh3-connect-github`) [O·m, §7 and §12]. One case is not more than one.
- **On main:** `pharn-spec.md` is 31,112 B, unchanged since 7.10.3 (`git log v7.10.3..HEAD` over the file prints nothing) [S·m], against a 32,768-byte ceiling: **1,656 B of headroom**. The
  ticket's 3,296 B was the 7.4.0 file (29,472 B, the measure recorded beside the ceiling). A consistency pass added
  to the spec stage would have about half the room the ticket assumed.
- **The stop costs the same on main** [advisory, a reading of the contract text]. S10 is still the closure row for any
  sub-stage ask (`pharn-loop.md:487`). The changes since 7.3.0 that let a loop continue past a SPEC problem all act after
  the grill, so none sees a plan-stage S10: re-plan rounds (7.8.0), the supervisor (7.9.0) and amend-spec (7.10.0). And
  amend-spec is append-only: every earlier criterion keeps its place, id, lines and verify level, and at least one is
  added. It can add a criterion; it cannot remove a contradiction between two existing ones.
- **Reopen when** a ledger set shows two or more stops caused by a contradiction between acceptance criteria (the
  ticket's own P7 bar: more than one read case).

## Reproduce

```bash
# byte counts at a ref (UTF-8, \r\n folded); §6 runs from the line starting "## 6. " to the line before "## 7. "
for ref in v7.3.0 v7.10.3 HEAD; do
  git show "$ref:pharn/ARCHITECTURE.md" | node -e 'const s=require("fs").readFileSync(0,"utf8").replace(/\r\n/g,"\n");
    const a=s.indexOf("\n## 6. ")+1, b=s.indexOf("\n## 7. ")+1, t=Buffer.byteLength(s), x=Buffer.byteLength(s.slice(a,b));
    console.log(process.argv[1], t, x, t-x)' "$ref"
  git show "$ref:.claude/commands/pharn-plan.md" | wc -c
  git show "$ref:.claude/commands/pharn-spec.md" | wc -c
done
grep -n '"pharn-plan.md"\|"pharn-spec.md"' .dev/floor/command-hygiene.test.mjs   # the two ceilings
```

`wc -c` equals the folded count on this all-LF repository. The figures above came from an equivalent script in the
session scratchpad (`git show` through `spawnSync`), not committed, as the CORE-88 record's was.
